以下分区是基于公开材料的工程判断，不代表任何本地系统已经升级或受影响。

## Adopt

**将依赖来源和锁定版本视为 Agent 的执行边界。** GitHub Advisory 将 `agent-framework` 1.26.1/1.26.2 列为恶意版本：安装后的 `.pth` 启动钩子会在解释器启动时执行并尝试窃取环境变量、凭证和云令牌。[2] 这是高成熟度、高紧急度的供应链事件；风险在于只看应用 imports，而忽略 CI 缓存、镜像层和内部镜像。下一步：在依赖清单、锁文件、构建缓存和镜像中检索两个版本；若命中，重建环境并按事件响应流程轮换可能暴露的凭证，不要以“升级到 latest”替代版本核验。

## Trial

**把动态工具目录收敛为稳定的三段式接口。** Pydantic AI 2.71.0 的 `ToolBridge` 将庞大或变化的工具集固定在 `tool_search`、`tool_describe`、`tool_call` 后方，以降低工具列表变化对 prompt cache 的影响。[1] 这是可试验的运行时能力；风险是搜索/描述阶段遗漏安全属性，或让模型误以为发现即授权。下一步：在非生产工作流中记录每次发现、描述和调用的工具版本、输入 schema、授权判定与输出摘要；为未命中、过期描述和权限拒绝分别写回归用例。

**把“结束前验证”变成 harness 规则，而非模型自觉。** 同一发布提供 `PermissionRule`，可按规则 allow/ask/deny 工具与 shell 调用，并增加 `RequireVerification`，在编码 Agent 未运行验证时将其送回检查。[1] 成熟度仍属快速演进框架功能，主要风险是规则覆盖不足、验证命令本身不可信，或失败后被错误地豁免。下一步：先只对写文件、网络、进程和发布工具采用默认拒绝；将测试命令和最小通过条件放进受版本控制的 policy，并把豁免原因写入 trace。

## Watch

**将公开排行榜当作回归探针，而非采购结论。** c0ze 项目本周把 Gemini 4 Neon、HY4、HY4 Flash 和 DeepSeek V4.1 Flash 纳入同一轮盲评；材料公开了任务数、评分子 Agent、运行日志与交叉检查信息。[3] 可复查性优于只发布单一分数，但 13 个任务和特定 harness 仍不足以代表真实仓库、权限模型或成本。下一步：选择其中两到三个与自身任务相近的题型，复刻“盲评 + 固定种子 + 失败日志保留”的方法，比较自己的版本变更前后，而不是直接照搬名次。

## Hold/Risks

- **不要把包名或组织名当作供应链证明。** 恶意版本可沿着缓存、内部制品库和基础镜像长期存活。[2]
- **不要让工具发现扩大权限。** 动态目录解决上下文与缓存问题，不授予执行权限；发现、审批和执行必须可区分、可审计。[1]
- **不要把“运行过测试”当成充分验证。** 验证命令需要受控版本、明确覆盖目标和可回收的日志；否则 `RequireVerification` 只会制造形式证据。[1]
- **不要用小样本排行榜替代自身评测。** 公开运行可帮助复现实验设计，但无法覆盖你的数据、工具权限与失败成本。[3]

## Practical Stack Adjustments

## 要解决的问题

面对动态工具、长链路编码任务与第三方依赖时，团队能否证明某次执行调用了哪一个工具版本、经过何种授权、运行了什么验证，并能追溯构建中是否出现已知恶意包？

## 最小抽象

为每次工具调用记录 `run_id`、`tool_catalog_version`、`tool_schema_hash`、`policy_decision`、`verification_command_digest`、`verification_result`、`package_lock_digest` 与 `effect_receipt`。这些字段进入 trace；不记录令牌、完整提示词或业务载荷。

## 工程闭环

1. 以锁文件和镜像 SBOM 建立依赖准入门槛；对撤回、恶意或未验证版本阻断构建，并扫描缓存和制品库。
2. 将动态工具目录拆为发现、描述、调用三个动作；调用前必须再次匹配 schema hash 与 policy decision。
3. 将写入、网络、shell 和发布操作默认设为拒绝或人工审批；将被批准的参数与 effect receipt 关联。
4. 对编码 Agent 固定验证命令、超时和最小通过条件；保留失败、重试和人工豁免的证据。
5. 每次 harness、模型或策略升级后，以固定任务集进行盲评回归，并用失败轨迹定位退化。

## 主线判断

本周应优先投资“可证明的执行”。供应链版本核验是立即行动项；工具桥接、权限规则和结束前验证适合在可回滚环境中试验；公开盲评的价值在于让团队把自身评测设计得更可复查。

## 直接结论

四条信号达到发布门槛，维持周更。先排查并阻断恶意 `agent-framework` 版本；随后在一个低风险编码工作流中，将动态工具目录、默认拒绝策略和强制验证串成一条带 trace 的闭环；最后用固定小任务集建立升级前后的盲评基线。

下一步阅读：先核验锁文件、镜像与 CI 缓存中是否存在 `agent-framework` 1.26.1/1.26.2；再为一个只读代码检索 Agent 演练“发现工具、请求调用、策略审批、运行验证、保存回执”的全链路。

## 小样本推演

假设一个修复建议 Agent 先用目录接口发现代码搜索和测试工具。发现阶段只返回名称、schema hash 与风险标签；当它请求运行 shell 测试时，策略按参数判断为 `ask`，批准记录与工具版本写入 trace。Agent 修改建议后触发受控测试命令；若测试未运行或失败，`RequireVerification` 阻止它宣称完成。执行环境则从锁文件和镜像 SBOM 排除已知恶意包版本，避免验证进程本身因安装依赖而泄露凭证。这个场景同时检验工具发现不等于授权、验证不等于口头承诺、依赖不等于可信来源。
