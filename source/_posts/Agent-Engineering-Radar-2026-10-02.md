## Adopt

**为工具目录、历史扫描和沙箱销毁设置显式资源边界。** OpenAI Agents SDK 0.23.0 增加了可配置的 MCP 列表页上限、可选的 Docker 删除保护、记忆 consolidation 回合数，以及加密历史扫描预算。[1] 这些都是运行时资源治理的明确控制面，适合纳入依赖升级评审；但 SDK 仍处于 0.x 快速演进阶段，配置默认值和兼容性需要在升级前核验。下一步：为一个远端 MCP 接入设定工具页上限、为一个可销毁沙箱启用保护，并记录超过历史扫描预算时的可观测降级行为。

## Trial

**把端云 Agent 的评测证据与部署证据收敛到同一个实验记录。** AgentWare 把环境准备、分布式部署、执行追踪、基础设施遥测和 LLM-as-a-Judge 评测放进一条端到端管线，并报告正确性、性能、资源利用率和能耗。[2] 它的价值在于提出可复现的生命周期，不代表该框架已适合所有个人栈；当前成熟度是公开研究与开源原型，异构环境、评判稳定性和运维成本都是风险。下一步：不必迁移框架，先为一条现有 Agent 流程把版本、部署目标、执行轨迹、延迟、token 与通过率写入同一实验清单。

## Watch

**观察“授权收据”能否成为 Agent 发布门槛的一部分。** 该研究提出：证据应绑定到具体工件和冻结的策略基线，批准与例外应精确限定作用域和时限，并在合并、部署等效果边界再次复核。[3] 这是值得吸收的治理模型，成熟度仍是预印本；论文也未声称已经证明生产优越性或法规合规。下一步：为一个写入型工具试做最小收据，关联工件版本、策略版本、验证结果、授权者、过期时间和最终执行 ID。

## Hold/Risks

- **暂缓把分页或扫描上限当成安全隔离本身**：它们控制规模，不会自动验证 MCP 工具来源、输出可信度或工具权限；仍需最小权限与服务端策略。[1]
- **暂缓把 LLM-as-a-Judge 分数直接当作端云发布依据**：AgentWare 展示的是统一实验路径，评判偏差、负载差异和资源测量方法仍需结合自身任务校准。[2]
- **暂缓只在审批时验证一次**：策略、依赖或目标工件在等待期间可能变化；高影响动作应在效果边界重新检查授权是否仍然匹配。[3]

## Practical Stack Adjustments

## 要解决的问题

当工具目录过大、记忆过长或审批后重试发生时，系统能否说明资源为何被消耗、证据对应哪个版本、以及这次动作是否仍然被允许？

## 最小抽象

把一次敏感运行表示为同一执行 ID 下的资源预算、工件版本、策略版本、验证证据和最终效果边界。

## 工程闭环

1. 为每个远端 MCP 接入定义工具枚举上限、超限处理和允许的工具来源；在追踪中保留命中上限的事件。
2. 为每次评测附上代码或提示版本、部署位置、模型、预算、延迟和资源指标，避免把环境漂移误判成能力变化。
3. 对写入、合并或发布动作保存最小授权收据，并在真正调用工具前重新核对工件摘要与策略版本。
4. 在 staging 演练三种失败：工具目录截断、历史扫描预算耗尽、审批后工件变化；三者都应有明确拒绝或降级结果。

## 主线判断

先把资源边界和证据边界放到同一执行记录中，再扩大端云部署与工具数量；否则很难区分成本异常、评测波动与授权失效。

## 小样本推演

假设一次部署在批准后切换了镜像摘要：即使原始评测通过，也应在执行边界发现摘要不匹配并要求重新验证或重新批准。反过来，若摘要、策略、预算与证据都仍匹配，才可以继续执行。这里是检查规则，不预设任何 SDK 或框架默认会这样处理。

## 直接结论

本期三条信号达到发布门槛，继续保持周更。优先为一个敏感工具调用建立“预算、证据、授权、执行”四项关联记录，再讨论更大规模的 MCP 工具目录或端云编排。
